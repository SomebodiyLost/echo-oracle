A scanner that thinks, with a human at the controls

Echo wraps the standard open-source recon tools behind one command and uses AI to cut scanner noise. Oracle, its reasoning engine, reads a finished run and surfaces the non-obvious, in-scope leads a checklist scanner walks past.

Echo

the data engine

Scope guardA fail-closed allowlist with three verdicts, re-checked on everything discovered.
Scannerssubfinder, httpx, nuclei, with opt-in nmap for ports.
Detection registrywhatweb, wafw00f, TLS and security headers; noisy tools stay opt-in.
AI triageSeparates real findings from scanner noise, with reasoning.
Report and dashboardPriority-ranked output and a live security console.

Oracle

the reasoning engine

WSTG methodologyReasons across the OWASP testing categories and maps what it can assess versus the gaps.
Method to inferenceEach lead carries a structured reasoning chain and an OWASP class.
CorrelationTies scattered findings to shared root causes instead of a flat list.
Multi-model cross-checkA second model from a different lab reviews the run; disagreements are flagged, not hidden.
Blind reconciliationA reviewer merges both assessments and settles the splits with reasoning.

What sets it apart

Finds the overlooked

Reasons about in-scope surface recon never examined: endpoints a spec reveals, paths a stack implies. Not just known-bad patterns.

Coverage gaps as a map

Reports which WSTG categories the evidence cannot yet assess, turning absence of findings into a to-do list rather than a false all-clear.

Two models, one verdict

Independent assessments from different labs, reconciled by a blind reviewer. Agreement raises confidence; disagreement earns your attention.

Read-only by design

Oracle proposes information-gathering checks and flags what a human should test by hand. It never exploits.

A scout, not an attacker

The line that keeps this legal to run and honest to present. These are enforced in the architecture, not just stated.

01
Authorized targets onlyNothing runs against a host that is not explicitly in the scope file. The guard fails closed.
02
Read-only reasoningThe AI analyzes and advises. It generates no payloads, logins, or exploits.
03
Human in the loopOracle proposes; a person reviews, runs the checks, and decides. Exploitation is always a deliberate human step.
04
Scope-gated actionsAnything the tool reasons toward still clears the hostname guard before a single packet is sent.

One pipeline, or step by step

Check scope first, always. Then run the whole pipeline in one command, or drive each stage yourself. The Stages tab explains what each one writes.

# confirm a target is in scope — sends nothing
python -m echov scope-check --target app.example.com

# full pipeline: scan, triage, detect, reason, report
python -m echov assess --target app.example.com

# or re-analyze a finished run: two models, then a blind reviewer merges them
python -m echov oracle crosscheck --reconcile

# view it live in the security console
python -m streamlit run dashboard/console.py

GUIDE/01 OF 05/SETUP

Install once, snapshot, then work from the snapshot

Echo Oracle runs on a dedicated Kali Linux VM. The scanners are Go binaries; the tool itself is a Python package. Practice targets run in Docker and bind to localhost only, so they are reachable from inside the VM and nowhere else.

1
ScannersInstall subfinder, httpx and nuclei with Go, and put ~/go/bin first on PATH so the ProjectDiscovery httpx wins over the Python package Kali ships under the same name.
2
ProjectClone, create a virtual environment, install the requirements.
3
KeysCopy .env.example to .env and add the Claude API key. The OpenAI key is only needed for the cross-check.
4
ScopeCopy scope.example.yaml to scope.yaml. Allow and deny lists, nothing else. An empty allow list blocks everything.
5
Verify and snapshotRun the version checks and a scope-check, then take a VM snapshot named tools-installed.
# 1 scanners (Go), PATH ordering matters
go install -v github.com/projectdiscovery/subfinder/v2/cmd/subfinder@latest
go install -v github.com/projectdiscovery/httpx/cmd/httpx@latest
go install -v github.com/projectdiscovery/nuclei/v3/cmd/nuclei@latest
echo 'export PATH=$HOME/go/bin:$PATH' >> ~/.zshrc && source ~/.zshrc
nuclei -update-templates

# 2 project
git clone https://github.com/SomebodiyLost/echo-oracle.git && cd echo-oracle
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# 3 keys, 4 scope
cp .env.example .env
cp scope.example.yaml scope.yaml

# 5 verify
which subfinder httpx nuclei
httpx -version && subfinder -version && nuclei -version
python -m echov scope-check --target juice.lab.local
Scope guard: ALLOW juice.lab.local matched allow rule "*.lab.local"

GUIDE/02 OF 05/THE FIVE STAGES

What each stage does, and what it leaves on disk

python -m echov assess runs them in this order and finishes with the Markdown report. Every stage can also be run on its own, and each reads the previous one's output from the run folder (the newest run unless you pass --run), so a re-run of Oracle never re-scans. No API key yet? --mock on triage, oracle analyze or assess uses offline reasoning at no cost.

1scope guard
Decides what may be touched. Every hostname, whether you typed it or a scanner discovered it, gets one of three verdicts. Blocked hosts are logged with the rule that blocked them. Fail-closed: a host with no matching rule is not scanned.
cmd python -m echov scope-check
in scope.yaml
out scope_decisions.json
2scan
Collects the raw surface. subfinder enumerates subdomains, httpx probes which ones answer and records them with their status codes as assets, nuclei runs its template checks against the live hosts. nmap port scanning is opt-in.
cmd python -m echov scan
in allowed hosts
out findings.json, assets.json
3triage
Separates findings from noise. The AI reads each nuclei result with its context, keeps what is real, suppresses what is not, and writes a one-line reason for each decision so you can disagree with it. Anything it cannot confirm from the evidence alone is flagged for human review.
cmd python -m echov triage
in findings.json
out triaged.json
4detect
Fingerprints the stack. whatweb and wafw00f identify the technologies and any WAF in front; the TLS and security-header checks record the baseline. Noisy detectors stay off unless enabled.
cmd python -m echov detect
in assets.json
out detections.json
5oracle
Reasons over the whole run. Reads everything above, maps it to the OWASP WSTG categories, correlates findings to shared root causes, and produces ranked leads plus a coverage map of what the evidence cannot yet assess, both in one analysis file. With crosscheck, a second model does the same independently; add --reconcile and a blind reviewer merges the two. For a deeper pass, oracle hunt proposes read-only, scope-gated fetches, waits for your approval on each, and re-reasons over what comes back, for up to six rounds.
cmd python -m echov oracle analyze then oracle report
in the full run folder
out oracle_analysis.json, oracle_analysis.html
then python -m echov report → report.md
·human review
Not a stage the tool runs. You read the leads in the report or the console, run the proposed checks by hand, and decide what, if anything, becomes a submission.
cmd python -m streamlit run dashboard/console.py
in report.md, oracle_analysis.html
out your call

verdict LEAD not in allow list (lookalike)
found by subfinder
log data/runs/.../scope_decisions.json
What to look at: nothing was sent. The host is named, the rule is named, and the same line appears in the report.

Re-analyze a finished run with the cross-check

Two models read the same evidence; neither sees the other's answer. Here they disagree.

python -m echov oracle crosscheck --reconcile
A HIGH exposed API spec (A01)
B MEDIUM exposed API spec (A05)
priority split high vs medium
reviewer HIGH reasoning attached
What to look at: the split itself. Disagreement is reported, not averaged away, and the reviewer has to say which priority it kept and why.

No findings is not an all-clear

A quiet run on a small target. Oracle reports what it could not assess.

python -m echov oracle analyze
leads 0
coverage 2/10 assessed
gaps WSTG-ATHN, WSTG-SESS, WSTG-INPV ...
next 3 manual checks proposed
What to look at: the gaps list. It is the to-do list for the human stage, and it is the reason the tool never says "secure".

GUIDE/04 OF 05/READING THE OUTPUT

The same colors and labels everywhere

Terminal, report and console use one legend. Severity is the triage verdict on a finding; the scope verdict is the guard's decision on a host; the lead fields are what Oracle attaches to every item it ranks.

SEVERITY · CVSS v3.1

  • CRIT
    Critical 9.0 – 10.0
    Verify by hand before anything else.
  • HIGH
    High 7.0 – 8.9
    Serious; usually one step from proof.
  • MED
    Medium 4.0 – 6.9
    Worth reporting; limited impact alone.
  • LOW
    Low 0.1 – 3.9
    Hygiene. Often the root cause of several mediums.
  • INFO
    Info 0.0
    Recorded for context. Not a finding.

LEAD PRIORITY · ORACLE

  • HIGH
    Look here first
    Oracle judges this the most worth investigating.
  • MED
    Worth a pass
    Plausible from the stack or the findings; needs a manual check to confirm.
  • LOW
    Background
    Hygiene or context. Usually explains other items rather than standing alone.

A separate axis from CVSS. Findings get a severity, up to Critical; leads only ever get high, medium or low. Every lead carries a read-only next check and a step to test by hand.

FLAGS

  • needs human review
    Set by triage
    The finding could not be confirmed from the evidence alone; the report says Verify manually. Example: an exposed /metrics endpoint where the scan did not capture the page contents.
  • priority split
    Set by crosscheck
    The two models gave the same lead different priorities. Shown as-is; with --reconcile the reviewer picks one and says why.

SCOPE VERDICT · GUARD

  • ALLOW
    In scope
    Matched an allow rule and no deny rule.
  • LEAD
    Blocked, worth a look
    Discovered but not in the allow list. Logged for you to add or ignore. Nothing sent.
  • DENY
    Blocked, explicitly
    Matched a deny rule. Logged with the rule, never scanned.

GUIDE/05 OF 05/DASHBOARD

The security console, reading the same run folder

A Streamlit app over the files the stages write. No database and no second copy of the data: what the terminal printed is what the console shows, with the suppressed items and scope decisions one click away.

localhost:8501 · security dashboard
# launch the console over the latest run
